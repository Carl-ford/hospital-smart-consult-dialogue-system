## 2. `场景二_知识库维护时序图.png`

**三处改动**（编号会从 1–55 变成 1–59）。

### 改动 1：图首的读取记录，外面要包一层 alt

| 位置 | 现在（旧 PNG） | 导出后应为 |
| --- | --- | --- |
| 图首 alt 区 | 直接就是 `alt` 的 `[读取失败] / [暂无记录] / [有记录]` 三支 | 外层多一层 `alt`，标签 `[参考未命中记录]`；并且多一个 `else 不参考，直接维护` 分支，里面一条消息 `跳过记录查看，直接进入维护` |

导出后，图首结构应变成：

```
[参考未命中记录]   ← 新增外层分支
   ├─ [读取失败]   显示暂时无法读取记录（不显示空列表）
   ├─ [暂无记录]   显示暂无记录，可直接维护
   └─ [有记录]     返回匿名记录列表 → 展示匿名未命中记录
[不参考，直接维护]  ← 新增分支
   └─ 跳过记录查看，直接进入维护
```

> 为什么要改：查看记录本来就是**可选**的（管理员可以看了记录再维护，也可以直接维护）。蒋诗韵《重点场景用例说明》3.3 有 **SC-02.P「直接维护」**，《需求范围追踪矩阵》也写明 UC-03 是"SC-02 可选入口"、UC-04/UC-05"**不强制**先查看记录"。旧图把读记录画成了必经第一步，会和她的文档直接冲突。

### 改动 2：删除分支的 `readEntry` 要多一跳

| 位置 | 现在（旧 PNG） | 导出后应为 |
| --- | --- | --- |
| 删除分支（原编号 40 附近） | 只有一条 `readEntry(知识编号)`，**从"管理后台界面"直接连到"知识条目管理服务"** | 变成**两条**：① 管理后台界面 → 知识条目管理服务 `readEntry(知识编号)`；② 知识条目管理服务 → 模拟知识库 `readEntry(知识编号)` |

### 改动 3：删除分支的失败来源要补上

| 位置 | 现在（旧 PNG） | 导出后应为 |
| --- | --- | --- |
| `[目标不存在/读取失败]` 分支 | 直接就是"知识条目管理服务 → 管理后台界面 `无法删除`"，**没有底层失败来源** | 前面补一条：模拟知识库 → 知识条目管理服务 `无法读取` |
| `[读取成功]` 分支 | 直接就是"知识条目管理服务 → 管理后台界面 `返回编号和标准问题`" | 前面补一条：模拟知识库 → 知识条目管理服务 `返回原条目` |

导出后，删除分支应变成（对齐编辑分支的写法）：

```
[删除知识条目]
  管理后台界面 → 知识条目管理服务 : readEntry(知识编号)
  知识条目管理服务 → 模拟知识库 : readEntry(知识编号)          ← 新增
  ├─ [目标不存在/读取失败]
  │     模拟知识库 → 知识条目管理服务 : 无法读取                 ← 新增
  │     知识条目管理服务 → 管理后台界面 : 无法删除
  └─ [读取成功]
        模拟知识库 → 知识条目管理服务 : 返回原条目               ← 新增
        知识条目管理服务 → 管理后台界面 : 返回编号和标准问题
        管理后台界面 → 管理员 : 展示删除对象，请求确认
        …
```

> 为什么要改：老图画的是"管理后台界面直接向 **知识条目管理服务** 调用 `readEntry`"，但类图里这个类**根本没有 readEntry 方法**（只有 add/update/delete/validateEntry）。而且"读取失败"这条分支缺了失败来源，等于无因之果。类图那边我已经给"知识条目管理服务"补上 `readEntry(id)`，两边就对上了。另：UC-06 主流程第 2 步"系统展示条目编号和标准问题，请管理员确认"——老图在类图层面其实**没有可用的读取路径**，这条是根因。

### 编号变化提示

新增消息共 4 条（入口分支 1 条 + 删除分支 3 条），所以：

- 原 **1–8** → 仍是 **1–8**（不变）

## 4. `设计类图.png`

**四处改动**。

| 位置 | 现在（旧 PNG） | 导出后应为 |
| --- | --- | --- |
| `知识条目管理服务` 类框 | 4 个方法：`addEntry` / `updateEntry` / `deleteEntry` / `validateEntry` | **5 个方法**，在 `addEntry` 下面插入一行<br>`+readEntry(id): KnowledgeEntry` |

| `知识匹配服务 → 模拟知识库` 连线标签 | `查询` | `查询/返回` |
| `知识条目管理服务 → 模拟知识库` 连线标签 | `写入` | `写入/读取` |

> 为什么加 `readEntry`：这是场景二删除分支能成立的**前提**——管理后台要"展示条目编号和标准问题供确认删除"，就必须有个能读条目的入口。加在"知识条目管理服务"上，时序图的两跳就顺了。

> 为什么补标签：`知识条目管理服务 → 模拟知识库` 实际既写入也读取；`知识匹配服务 → 模拟知识库` 是"查询并返回条目"，只写"查询"漏了返回值。
