# 《医院门诊智能应答与对话系统》四框架架构分析文档

> 方法论：Bolman & Deal《Reframing Organizations》组织四框架模型
> 结构框架 · 人力资源框架 · 政治框架 · 象征框架
>
> 本文档基于 Bolman & Deal 四框架模型，从组织分工、人员匹配、干系人诉求、团队文化四个视角分析本课程项目。

---

## 一、结构框架（Structural Frame）

结构框架关注正式分工、角色职责、汇报关系与协调控制机制。本项目采用"组长统筹 + 专业组并行"的组织方式，以 RACI 责任矩阵和统一归档路径实现分工清晰、责任到人。

### 1.1 正式分工与汇报结构

项目共 8 名成员，按产出物性质分工，组长位于顶层统筹：

| 组别 | 成员 | 主要产出 |
|------|------|----------|
| 项目组长 | 杨卓屹 | 撰写需求说明书、统筹进度、终审全部产出 |
| UML 建模组 | A 蒋诗韵、B 王宇坤 | A：用例图、活动图、状态图；B：类图、时序图、对象图 |
| 文档组 | C 何亭玉、D 张天乐 | C：十大知识域文档、预期目标分析；D：四框架架构分析文档 |
| 管理图组 | E 钱智超 | 人力架构图、进度甘特图、风险状态图 |
| 整合组 | F 詹少希、G 林泽楷 | F：报告主笔与整合；G：格式、引用与图文一致性核对 |

汇报路径为：各组组员 → 组长。整合组 F/G 作为素材收口节点，接收各组产出后由组长终审。

### 1.2 RACI 责任矩阵

每项交付物指定唯一最终负责人（A），详见 `成员描述与分工.md`。要点：

- 需求说明书、项目初步计划、最终提交：组长为 A；
- 六张 UML 图：A、B 为 R，组长为 A；
- 知识域与预期目标文档：C 为 R；
- 四框架文档：D 为 R；
- 三张项目管理图：E 为 R；
- 报告整合：F 为 R；格式与图文一致性：G 为 R。

### 1.3 协调与控制机制

- **范围控制**：明确本次作业范围与项目边界（见 README），不包含 HIS 核心业务、代码开发、部署运维。
- **进度控制**：9/14–16 需求与初步计划定稿；9/16–17 各组完成初稿；9/18 12:00 前素材统一交付整合组；9/19 24:00 终稿；9/20 课程提交。
- **归档控制**：所有产出统一归档至 GitHub 仓库，文档入 `docs/`、图纸入 `diagrams/`，文件名与 README 一致，便于整合时定位。
- **质量控制**：组员自检、跨组交叉检查、组长终审三级流程，不合格打回。

## 二、人力资源框架（Human Resource Frame）

人力资源框架关注成员能力与人岗匹配、沟通机制与团队协作。本项目的基本安排是：让具备相应能力的成员承担对应产出。

### 2.1 能力与人岗匹配

- **A/B（UML 建模）**：A 负责行为视角（用例/活动/状态），B 负责结构视角（类/时序/对象），两人职责互补。
- **C/D（文档）**：C 负责十大知识域与预期目标，D 负责四框架分析。
- **E（管理图）**：独立产出人力架构图、甘特图、风险状态图。
- **F/G（整合）**：F 主笔贯通全文，G 负责格式、引用与图文一致性。
- **组长**：负责需求定义与最终审核，不替代专业组执行。

### 2.2 沟通机制

- **三级沟通链路**：组长统筹（定方向、下基线）→ 节点对接（各组按 9/18 节点交付素材）→ 集中收口（F/G 整合）。
- **交付规则**：先自检、后交付；统一命名归档；问题即时打回修正。
- **交叉检查**：跨组核对术语与逻辑一致性，同时让成员在过程中了解其他组的产出。

### 2.3 协作保障

课程项目以课程成绩为目标，通过"每项成果唯一负责人"明确归属。各组在截止日期前自行安排课余工时，遇阻塞及时在沟通链路中提出。

## 三、政治框架（Political Frame）

政治框架识别核心干系人的诉求差异与协调方式。本项目涉及四类干系人：课程评审老师、医院（业务场景代表）、患者（系统使用者）、项目团队。

### 3.1 干系人诉求

| 干系人 | 核心诉求 | 对项目的约束 |
|--------|----------|--------------|
| 课程评审老师 | 项目管理方法论落地、不套模板 | 每个知识域与分析维度要有对应真实产出 |
| 医院（场景方） | 导诊负担减轻、答复口径统一、不越诊疗边界 | 不做诊断、处方、挂号收费等核心业务 |
| 患者（使用者） | 问答快、答复清晰、非接诊时段也可查 | 系统返回标准化流程指引，不猜测答案 |
| 项目团队 | 按期交付、文档规范、课程成绩达标 | 范围清晰、节点明确 |

### 3.2 主要协调点

- **患者希望系统回答一切 vs 医院不能让自助系统介入诊疗**：本项目的处理方式是——模拟知识库未命中时，系统不猜测答案，提示患者前往线下导诊渠道，并匿名记录该问题供后续知识库补充。这样既守住"不越界"的边界，又让患者的问题被记录。
- **团队想多做功能 vs 课程要求范围清晰**：本次作业只做需求设计与 UML 建模，代码开发、真实接口、部署运维均列为范围外。
- **各组进度不一 vs 整合组需要统一收口**：以 9/18 12:00 为素材交付硬节点，组长在节点处行使打回权。

### 3.3 团队内部协调

组长掌握需求基线与最终审核权，F/G 负责报告如何组织与表述。这种分工通过 RACI 矩阵明确，避免职责重叠。

## 四、象征框架（Symbolic Frame）

象征框架关注团队在作业过程中形成的共同规范与项目呈现方式。

### 4.1 统一命名与归档

仓库中所有文件按"组员代号_图名"或统一文档名命名（如 `A_用例图.png`、`B_类图.png`），文档统一放在 `docs/`，图纸统一放在 `diagrams/`。命名规范本身是课程作业规范性的体现。

### 4.2 三级审核作为共同规范

- 组员自检：产出后对照需求先自查；
- 交叉检查：跨组核对术语与逻辑一致性；
- 组长终审：不合格打回。

这套流程是团队共同遵守的质量规范，向评审老师说明：我们在设计阶段就进行了交叉检查，而不是最后才统一通读。

### 4.3 项目定位

本项目作为课程设计原型，定位是"门诊前置咨询的流程指引工具"，基于模拟知识库完成需求与建模，不模拟真实诊疗行为。这一定义既贴合课程要求，也为后续迭代预留了空间。

## 五、四框架协同

四个框架是同一项目的四个视角：

- **结构框架**：谁做什么、怎么控制——分工、RACI、阶段节点、归档；
- **人力资源框架**：人如何匹配与沟通——能力对应、三级沟通、交叉检查；
- **政治框架**：各方诉求如何协调——评审老师、医院、患者、团队的差异与妥协；
- **象征框架**：共同规范与项目定位——命名规范、三级审核、原型边界。

结构提供骨架，人力落实到人，政治处理诉求差异，象征统一规范。
